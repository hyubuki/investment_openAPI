# External Securities OpenAPI 용어사전 및 업무 기준

## 1. 문서 목적
이 문서는 External Securities OpenAPI 프로젝트에서 사용하는 용어와 시스템 경계를 통일하고, 설계·구현·리뷰·테스트를 수행하는 공통 기준을 정의한다.
주문 및 체결 시스템에서는 같은 단어를 서로 다르게 해석하면 금전적 손실이나 장애로 이어질 수 있다. 따라서 코드, API 명세, 데이터베이스, 로그, 대시보드 및 업무 대화에서는 이 문서의 용어를 우선 사용한다.
기존 정의를 변경할 때는 영향을 받는 API, 상태 전이, 저장 데이터 및 이벤트 소비자를 함께 검토한다.

## 2. 시스템 범위와 주체

### 2.1 전체 흐름

```text
External Client
    │ HTTPS REST: 주문·정정·취소
    ▼
External OpenAPI
    │ 내부 명령
    ▼
Trading Module / OMS
    │ 거래소 전용 프로토콜
    ▼
Exchange Gateway
    │ 전용 네트워크 및 TCP 기반 세션
    ▼
Stock Exchange / Matching Engine
    ▲
    │ 상대 주문
Other Securities Firm

체결 결과:
Stock Exchange → Exchange Gateway → OMS → Event Broker → WebSocket Gateway → External Client
```

상대 증권사와 우리 증권사가 직접 주문을 매칭하지 않는다. 각 증권사의 주문이 거래소 Matching Engine으로 유입되고 거래소가 반대 주문을 매칭한다.

### 2.2 구성요소 용어

| 용어 | 정의 |
|---|---|
| External Client | B2C OpenAPI를 사용해 본인 계좌를 조회하거나 주문하는 개인 투자자 애플리케이션 |
| External OpenAPI | 인증, 인가, 요청 검증, Rate Limit, API 버전 관리 및 외부 계약을 담당하는 경계 |
| Order Service | 주문 생성, 상태 전이, 정정·취소 규칙 및 주문 불변식을 처리하는 매매 모듈 Service |
| OMS | Order Management System. 주문의 전체 Lifecycle과 현재 상태를 관리하는 시스템 |
| Execution Service | 거래소 체결 통보를 검증하고 주문 누적 체결 수량, 잔량, 평균 체결가 등을 반영하는 매매 모듈 Service |
| Exchange Gateway | 내부 주문 모델과 거래소 프로토콜 사이를 변환하고 세션, 순번, 재전송 및 연결 복구를 담당하는 어댑터 |
| Stock Exchange | 주문을 접수하고 시장 규칙에 따라 처리하는 거래소 |
| Matching Engine | 가격·시간 우선순위 등 거래소 규칙에 따라 매수·매도 주문을 매칭하는 엔진 |
| Order Book | 거래소가 아직 체결되지 않은 매수·매도 주문을 가격 및 우선순위에 따라 관리하는 호가장 |
| Counterparty | 거래소에서 우리 주문과 체결된 반대편 주문의 당사자. 다른 증권사 고객일 수도 있고 같은 증권사 고객일 수도 있음 |
| Event Broker | 체결 및 주문 상태 이벤트를 서비스 간에 전달하고 일시적인 트래픽 급증을 흡수하는 내부 메시징 시스템 |
| WebSocket Gateway | 인증된 External Client 연결과 구독을 관리하고 주문·체결 이벤트를 실시간 전송하는 시스템 |
| Source of Truth | 특정 데이터의 최종 상태를 판단하는 권위 있는 저장소. 주문·체결의 기준은 OMS 및 체결 원장이며 WebSocket 연결이 아님 |

## 3. 주문과 체결 용어

| 용어 | 정의 |
|---|---|
| Order | 특정 상품을 정해진 조건으로 매수하거나 매도하려는 의사 표시 |
| New Order | 신규 주문 |
| Replace Order | 기존 주문의 가격 또는 수량을 변경하는 정정 주문. 시장 규칙에 따라 가능한 범위와 우선순위 영향이 달라짐 |
| Cancel Order | 기존 주문의 미체결 잔량을 취소하는 요청 |
| Buy | 매수 |
| Sell | 매도 |
| Limit Order | 지정가 주문. 매수는 지정가 이하, 매도는 지정가 이상에서 체결 가능 |
| Market Order | 시장가 주문. 가격을 지정하지 않고 시장 규칙에 따라 체결 가능한 가격을 우선하는 주문 |
| Marketable Limit Order | 현재 반대편 호가와 즉시 매칭할 수 있는 지정가 주문 |
| Last Traded Price | 현재가로 표시되는 가장 최근의 체결 가격. 현재 최우선 매수·매도 호가와 다를 수 있음 |
| Bid | 매수 호가 |
| Ask | 매도 호가 |
| Execution / Fill | 거래소에서 매수 주문과 매도 주문이 매칭되어 거래가 성립한 결과 |
| Partial Fill | 주문 수량의 일부만 체결된 상태 |
| Full Fill | 주문 수량 전체가 체결된 상태 |
| Cumulative Quantity (`cumQty`) | 지금까지 누적 체결된 수량 |
| Leaves Quantity (`leavesQty`) | 아직 체결되거나 취소되지 않은 주문 잔량 |
| Last Quantity (`lastQty`) | 가장 최근 개별 체결에서 체결된 수량 |
| Last Price (`lastPrice`) | 가장 최근 개별 체결 가격 |
| Average Price (`avgPrice`) | 누적 체결 금액을 누적 체결 수량으로 나눈 평균 체결가 |
| Execution Report | 주문 접수, 거부, 체결, 취소 등 거래소 처리 결과를 통보하는 메시지의 일반적 표현 |
| Clearing | 체결 이후 결제 의무를 확정하고 상계하는 청산 과정 |
| Settlement | 확정된 의무에 따라 증권과 대금을 실제로 이전하는 결제 과정 |

## 4. 식별자

| 식별자 | 발급 주체 | 목적 |
|---|---|---|
| `idempotencyKey` | External Client | 동일 주문 요청의 재시도로 중복 주문이 생성되는 것을 방지 |
| `clientOrderId` | External Client | Client가 자신의 주문을 추적하기 위한 식별자 |
| `orderId` | 우리 증권사 | 시스템 전체에서 사용하는 내부 주문 식별자 |
| `exchangeOrderId` | 거래소 | 거래소가 접수한 주문을 식별 |
| `executionId` | 거래소 또는 내부 표준화 계층 | 개별 체결을 식별하고 중복 체결 반영을 방지 |
| `eventId` | 이벤트 발행 시스템 | 개별 이벤트의 고유 식별자 |
| `sequence` | 세션 또는 이벤트 스트림 | 메시지 순서 확인과 누락 이벤트 복구에 사용 |
| `correlationId` | 최초 요청 수신 계층 | 하나의 요청이 여러 서비스와 메시지를 거치는 과정을 추적 |

식별자의 범위와 유일성 조건은 API 및 데이터 모델 설계 시 명시한다. 특히 `clientOrderId`와 `idempotencyKey`를 같은 의미로 사용하지 않는다.

## 5. 주문 Lifecycle

### 5.1 표준 상태

| 상태 | 의미 | 종료 상태 |
|---|---|---|
| `RECEIVED` | External OpenAPI가 주문 요청을 수신함 | 아니오 |
| `PENDING_NEW` | 내부 검증을 통과하고 거래소 접수 결과를 기다리는 중 | 아니오 |
| `NEW` | 거래소가 주문을 접수했으며 미체결 잔량이 존재함 | 아니오 |
| `PARTIALLY_FILLED` | 일부 수량이 체결되고 미체결 잔량이 존재함 | 아니오 |
| `FILLED` | 주문 수량이 전량 체결됨 | 예 |
| `PENDING_CANCEL` | 취소 요청을 전송하고 거래소 결과를 기다리는 중 | 아니오 |
| `CANCELED` | 거래소가 미체결 잔량의 취소를 확정함 | 예 |
| `PENDING_REPLACE` | 정정 요청을 전송하고 거래소 결과를 기다리는 중 | 아니오 |
| `REJECTED` | 신규 주문이 내부 또는 거래소 검증에서 거부됨 | 예 |
| `EXPIRED` | 시장 규칙 또는 유효기간 만료로 주문 효력이 종료됨 | 예 |
| `UNKNOWN` | 장애 또는 메시지 누락으로 거래소 최종 상태를 확정할 수 없어 대사가 필요한 상태 | 아니오 |

### 5.2 기본 상태 전이

```text
RECEIVED
   ↓
PENDING_NEW ───────────────→ REJECTED
   ↓
NEW ─────────→ PARTIALLY_FILLED ─────────→ FILLED
 │                    │
 │                    └─→ PENDING_CANCEL ─→ CANCELED
 ├─→ PENDING_CANCEL ─────────────────────→ CANCELED
 ├─→ PENDING_REPLACE
 └─→ EXPIRED
```

실제 상태 전이는 거래소 규칙과 내부 OMS 계약을 확인하여 확정한다. 취소 요청과 체결 통보가 동시에 발생할 수 있으므로 `PENDING_CANCEL`은 체결을 막는 상태가 아니다. 이미 체결된 수량은 취소할 수 없으며 취소는 미체결 잔량에만 적용된다.

### 5.3 반드시 구분할 결과

```text
HTTP 요청 성공
≠ 내부 주문 검증 성공
≠ 거래소 주문 접수 성공
≠ 체결 성공
```

- `HTTP 202 Accepted`: 주문 요청을 비동기로 접수했다는 의미다.
- Exchange ACK: 거래소가 주문을 정상 접수했다는 의미다.
- Execution: 실제 매매가 성립했다는 의미다.

API 응답과 이벤트는 현재 어느 단계까지 확정되었는지를 모호하지 않게 표현해야 한다.

## 6. 통신 채널 기준

| 구간 | 기본 방식 | 역할 |
|---|---|---|
| External Client → External OpenAPI | HTTPS REST | 주문·정정·취소 명령과 조회 |
| External OpenAPI → External Client | WebSocket | 주문 상태 및 체결 이벤트 실시간 전달 |
| External Client → External OpenAPI | REST Replay API | 연결 단절 중 누락된 이벤트와 최종 상태 복구 |
| 증권사 ↔ 거래소 | 전용 네트워크의 TCP 기반 장기 세션 및 거래소 프로토콜 | 주문 전송, 접수·거부·체결 통보, 세션 순번과 재전송 관리 |
| 내부 서비스 간 | 동기 호출 및 Durable Event Broker | 즉시 검증과 비동기 이벤트 전파를 역할에 따라 분리 |

WebSocket은 체결 원장이 아니라 빠른 알림 채널이다. WebSocket을 연결하지 않은 동안에도 주문과 체결은 정상 처리되어야 하며 Client는 재연결 후 REST 또는 Replay 프로토콜로 상태를 복구할 수 있어야 한다.

SSE는 단방향 체결 알림만 필요한 단순 Client를 위한 선택지로 검토할 수 있다. 본 프로젝트의 기본 스트리밍 방식은 시세, 주문 및 체결 채널을 확장하기 쉬운 WebSocket으로 가정하되, 최종 결정은 예상 트래픽과 B2C 서비스 요구사항을 근거로 ADR에 기록한다.

## 7. 메시지 처리와 신뢰성 원칙

### 7.1 즉시 처리 원칙

주문과 체결은 건by건으로 즉시 처리한다. 내부 큐에 쌓아두고 배치로 처리하지 않는다.
- 주문은 인증, 권한, 계좌, 상품, 주문 가능 금액·수량 및 리스크 검증 후 즉시 거래소로 전송한다.
- 체결은 OMS와 체결 원장에 반영한 트랜잭션이 커밋된 후 즉시 이벤트로 발행한다.
- 내부 큐는 정상 상황에서 지연을 만들기 위한 장치가 아니라 순간적인 트래픽 급증, 서비스 분리 및 장애 복구를 위한 장치다.
- TCP 패킷 병합과 애플리케이션 이벤트 배치는 구분한다. 네트워크 계층에서 패킷이 합쳐져도 주문 및 체결 이벤트의 논리적 경계는 유지한다.

### 7.2 전달 보장
- 외부 스트림은 `at-least-once` 전달을 기본 가정으로 한다.
- Client는 `executionId` 또는 `eventId`로 중복 이벤트를 제거할 수 있어야 한다.
- 이벤트마다 복구 가능한 `sequence`를 제공한다.
- 순서 보장 범위는 전역이 아니라 계좌, 주문 또는 스트림 파티션 등 명시된 단위로 제한한다.
- 체결 저장과 이벤트 발행 사이의 유실을 방지하기 위해 Transactional Outbox 또는 동등한 패턴을 사용한다.
- Redis Pub/Sub처럼 구독자가 없을 때 이벤트가 사라지는 기능을 체결의 유일한 전달·보관 수단으로 사용하지 않는다.

### 7.3 Backpressure와 Slow Consumer

- WebSocket 세션별 송신 큐는 반드시 크기가 제한된 bounded queue로 구성한다.
- 느린 Client 때문에 전체 시스템의 메모리나 처리 스레드가 고갈되지 않도록 격리한다.
- 큐 한도를 초과한 Client는 명시적인 오류와 마지막 안전 sequence를 제공한 뒤 연결을 종료하고 Replay를 요구한다.
- 체결 이벤트는 삭제하거나 최신 값으로 합치지 않는다.
- 시장 데이터는 상품 특성과 계약에 따라 중간 값을 생략하는 conflation 또는 snapshot 재동기화를 사용할 수 있다.

### 7.4 과부하 처리

- 시스템이 처리할 수 없는 주문을 무제한으로 수락해 내부 큐에 쌓지 않는다.
- 사용자, 계좌 및 주문 유형별 Rate Limit과 리스크 한도를 적용한다.
- 허용 용량을 넘으면 명확한 오류 코드와 재시도 가능 여부를 반환한다.
- 거래소 전송 지연, 내부 큐 깊이 및 가장 오래 대기한 주문의 시간을 핵심 운영 지표로 관리한다.

## 8. 일관성 및 동시성 기준

- 주문 상태 전이는 명시된 상태 머신과 낙관적 잠금 또는 동등한 동시성 제어를 거쳐야 한다.
- 같은 주문에 대한 체결, 취소 및 정정 이벤트가 경쟁할 수 있음을 기본 전제로 한다.
- 개별 체결은 `executionId`를 기준으로 멱등하게 반영한다.
- `cumQty + leavesQty + canceledQty` 등 수량 불변식을 매매 Service에서 검증한다. 정확한 공식은 거래소의 정정·취소 모델에 맞춰 확정한다.
- 금액과 가격은 부동소수점 타입을 사용하지 않고 `BigDecimal` 또는 최소 호가 단위 기반 정수로 표현한다.
- Client 타임스탬프를 체결 순서의 기준으로 사용하지 않는다. 거래소 sequence, 거래소 시각 및 내부 수신 시각을 구분해 보관한다.
- 장애 후 거래소 원장과 내부 원장이 다를 가능성을 고려하여 Reconciliation 절차를 제공한다.

## 9. 보안 및 감사 기준

- 모든 External API는 인증, 인가, 계좌 접근 권한 및 주문 권한을 검증한다.
- API Key 또는 Access Token뿐 아니라 요청 서명, timestamp 및 nonce 적용 여부를 검토한다.
- 민감정보와 인증정보는 로그에 남기지 않는다.
- 주문 생성, 정정, 취소, 거부 및 체결에 대한 감사 이력을 불변 형태로 보관한다.
- 운영자 수동 개입도 행위자, 사유, 이전 값 및 변경 값을 기록한다.
- 로그의 `correlationId`, `orderId`, `exchangeOrderId`, `executionId`로 전체 흐름을 추적할 수 있어야 한다.

## 10. 앞으로의 업무 진행 방식

기능 개발은 화면이나 Controller부터 시작하지 않고 아래 순서로 진행한다.

### 10.1 업무 모델과 계약 정의
1. 업무 용어와 시스템 경계를 이 문서에 정의한다.
2. 정상 흐름과 실패 흐름을 Sequence Diagram으로 작성한다.
3. 주문 상태, 상태 전이 조건, 불변식 및 종료 상태를 정의한다.
4. 외부 API의 요청·응답·오류 코드와 비동기 이벤트 Schema를 정의한다.
5. 내부 모델, 외부 API 모델 및 거래소 모델을 분리한다.

### 10.2 장애와 동시성 검토

각 기능은 구현 전에 최소한 다음 질문에 답한다.
- 동일 요청이 재전송되면 중복 주문 또는 중복 체결이 발생하지 않는가?
- 거래소로 전송한 직후 내부 시스템이 종료되면 상태를 어떻게 복구하는가?
- 거래소 ACK 또는 체결 메시지가 누락되거나 중복되거나 순서가 바뀌면 어떻게 처리하는가?
- 체결과 취소가 동시에 도착하면 어떤 상태가 최종 상태인가?
- DB Commit 이후 이벤트 발행에 실패하면 어떻게 재시도하는가?
- WebSocket Client가 느리거나 연결되지 않았을 때 어떻게 복구하는가?
- 내부 상태와 거래소 상태가 다르면 어떻게 탐지하고 대사하는가?

### 10.3 구현 원칙

- 업무 Service가 주문 및 체결 규칙과 트랜잭션 경계를 관리한다.
- Controller, JPA Entity, 거래소 DTO에 핵심 업무 규칙을 분산하지 않는다.
- External API 모델과 레거시·거래소 전문 사이에는 명시적인 변환 Adapter를 둔다.
- 트랜잭션 경계를 명시하고 외부 네트워크 호출을 DB 트랜잭션 안에서 장시간 수행하지 않는다.
- 재시도는 멱등성이 보장되는 작업에만 적용하고 횟수, 간격 및 종료 조건을 명시한다.
- 예외를 단순 문자열로 노출하지 않고 안정적인 오류 코드와 재시도 가능 여부를 제공한다.

### 10.4 테스트 원칙

기능별로 다음 테스트를 작성한다.

- 주문 상태 머신 단위 테스트
- 금액, 수량, 호가 단위 및 시장 규칙 경계값 테스트
- 동일 주문·체결 중복 수신에 대한 멱등성 테스트
- 체결·취소·정정 경쟁 조건에 대한 동시성 테스트
- Repository와 PostgreSQL 제약 조건 통합 테스트
- Redis 장애, Event Broker 장애 및 거래소 연결 단절 테스트
- WebSocket 재연결, sequence gap 및 Replay 테스트
- API 인증·인가, 계좌 격리 및 Rate Limit 테스트
- 예상 Peak보다 높은 부하에서 지연 시간, 큐 깊이 및 오류율을 확인하는 성능 테스트

Mock 기반 성공 테스트만으로 완료로 판단하지 않는다. 금전과 주문 상태에 영향을 주는 경로는 실제 데이터베이스와 메시징 환경을 포함한 통합 테스트를 우선한다.

### 10.5 관측성과 운영 준비

기능을 배포하기 전에 다음 지표와 운영 절차를 준비한다.

- 주문 접수부터 거래소 전송까지의 지연 시간
- 거래소 전송부터 ACK 및 체결 수신까지의 지연 시간
- 주문 상태별 건수와 비정상 장기 체류 주문 수
- 내부 Queue Lag, Queue Depth 및 Oldest Message Age
- WebSocket 연결 수, 송신 지연 및 Slow Consumer 수
- 중복 메시지, sequence gap, 재처리 및 대사 불일치 건수
- 거래소 연결 단절 및 재연결 횟수
- 장애 시 중단, 재처리, 대사 및 고객 안내 Runbook

### 10.6 설계 결정 기록

다음과 같이 장기간 영향을 미치는 선택은 ADR(Architecture Decision Record)로 남긴다.

- WebSocket과 SSE의 선택 및 지원 범위
- Event Broker와 파티셔닝 기준
- 주문 및 체결 데이터의 일관성 모델
- Transactional Outbox 구현 방식
- 거래소 세션 이중화와 복구 전략
- 멱등성 키의 범위와 보존 기간
- 이벤트 Replay 기간과 순서 보장 범위

## 11. 완료 기준

기능은 다음 조건을 모두 만족해야 완료된 것으로 본다.

- 업무 용어와 상태 전이가 문서 및 코드에서 일치한다.
- API 계약과 이벤트 Schema가 정의되고 버전 호환성이 검토되었다.
- 정상 흐름뿐 아니라 중복, 지연, 역순, 타임아웃 및 부분 장애가 테스트되었다.
- 주문·체결 데이터의 유실 및 중복 방지 근거가 설명 가능하다.
- 보안, 감사 로그, 메트릭 및 알람이 준비되었다.
- 장애 복구와 Reconciliation 절차가 문서화되었다.
- 성능 목표와 측정 결과가 기록되었다.
- 변경된 설계와 용어가 이 문서 또는 관련 ADR에 반영되었다.

## 12. 초기 설계 기준과 미확정 항목

### 현재 기준

- 주문·정정·취소 명령은 HTTPS REST를 사용한다.
- 실시간 주문 상태 및 체결 알림은 WebSocket을 기본안으로 한다.
- Client 연결 여부와 무관하게 OMS 및 체결 원장이 최종 상태를 보관한다.
- 누락 이벤트 복구를 위한 REST 조회 또는 sequence 기반 Replay를 제공한다.
- 주문과 체결은 정상 상황에서 이벤트 단위로 즉시 처리한다.

### 추후 확정할 항목

- 대상 거래소별 실제 주문·체결 프로토콜과 세션 규칙
- WebSocket 채널 구조, 메시지 Schema 및 Replay 보존 기간
- 계좌·주문·Client 단위의 정확한 순서 보장 범위
- Event Broker 선정과 Partition Key
- 주문 상태 모델과 내부 레거시 OMS 상태의 매핑
- 거래소 장애 및 장 운영 상태별 주문 접수 정책
- 사용자 등급별 Rate Limit, 최대 연결 수 및 구독 한도
- B2B 기관 고객과 FIX API는 별도 프로젝트 범위로 검토

미확정 항목은 임의로 구현에 고정하지 않는다. 요구사항, 거래소 규정, 내부 레거시 계약 및 예상 트래픽을 확인한 뒤 ADR로 결정한다.
