# 매매 업무 모듈

상태: `Draft v0.1`

상세 계약: [매매 API Spec](../api/매매-API.md)

## 1. 책임과 경계

매매 모듈은 신규 주문, 정정, 취소, 거래소 접수 결과, 부분·전량 체결 및 주문 상태 머신을 관리한다.

- 계좌 상태와 권한은 계좌 모듈에 질의한다.
- 주문 가능 여부와 한도는 리스크·한도 모듈이 판단한다.
- 상품, 호가 단위 및 시장 세션은 시장 모듈의 조회 결과를 사용한다.
- 체결에 따른 현금·증권 변동은 내부 메시지를 통해 원장 모듈에 전달한다.
- 거래소 전문은 Exchange Connectivity Adapter가 변환한다.

## 2. JPA Entity

### Order Entity

| 필드 | 타입 | 설명 |
|---|---|---|
| `orderId` | UUID | 내부 주문 식별자 |
| `clientOrderId` | String | Client 주문 식별자 |
| `accountId` | UUID | 주문 계좌 |
| `instrumentId` | UUID | 상품 식별자 |
| `market` | String | 주문 시장 코드 |
| `side` | OrderSide | `BUY`, `SELL` |
| `orderType` | OrderType | `LIMIT`, `MARKET` 등 |
| `timeInForce` | TimeInForce | `DAY`, `IOC`, `FOK`, `GTC` 등 시장 지원 범위 |
| `orderQuantity` | BigDecimal | 최초 주문 수량 |
| `limitPrice` | BigDecimal? | 지정가 주문 가격 |
| `cumulativeQuantity` | BigDecimal | 누적 체결 수량 |
| `leavesQuantity` | BigDecimal | 미체결 잔량 |
| `canceledQuantity` | BigDecimal | 취소 확정 수량 |
| `averagePrice` | BigDecimal? | 누적 평균 체결가 |
| `status` | OrderStatus | 주문 상태 |
| `exchangeOrderId` | String? | 거래소 주문 식별자 |
| `rejectionCode` | String? | 거부 사유 코드 |
| `receivedAt` | Instant | OpenAPI 수신 시각 |
| `submittedAt` | Instant? | 거래소 송신 시각 |
| `acceptedAt` | Instant? | 거래소 접수 시각 |
| `completedAt` | Instant? | 종료 상태 도달 시각 |
| `version` | long | 상태 전이 동시성 제어 |

불변식:

- 지정가 주문에는 `limitPrice`가 반드시 존재하며 시장가 주문에는 존재하지 않는다.
- 수량과 가격은 양수이며 상품별 단위와 시장 가격제한을 만족해야 한다.
- `cumulativeQuantity`, `leavesQuantity`, `canceledQuantity`는 음수가 될 수 없다.
- 체결 및 취소 반영 후 수량 합계는 주문 Lifecycle 규칙과 일치해야 한다.
- `FILLED`, `CANCELED`, `REJECTED`, `EXPIRED`는 종료 상태다.
- `PENDING_CANCEL` 상태에서도 거래소 체결이 먼저 확정될 수 있다.

### Execution Entity

Execution은 Order와 연결되는 불변 체결 기록이다. 기존 Row를 수정하지 않고 오류 정정은 별도의 반대 기록 또는 거래소 정정 규칙으로 처리한다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `executionId` | String | 개별 체결 고유 식별자 |
| `orderId` | UUID | 내부 주문 식별자 |
| `exchangeOrderId` | String | 거래소 주문 식별자 |
| `executionPrice` | BigDecimal | 체결 가격 |
| `executionQuantity` | BigDecimal | 체결 수량 |
| `liquidityRole` | LiquidityRole? | Maker/Taker 등 제공 시 기록 |
| `executedAt` | Instant | 거래소 체결 시각 |
| `receivedAt` | Instant | 내부 수신 시각 |
| `exchangeSequence` | String/long | 거래소 메시지 순번 |

`market + tradingDate + executionId` 또는 거래소가 보장하는 동등한 범위에 Unique Constraint를 둔다.

### OrderInstruction Entity

정정·취소 명령과 거래소 처리 결과를 감사 가능한 형태로 기록한다.

| 필드 | 설명 |
|---|---|
| `instructionId` | 명령 식별자 |
| `orderId` | 대상 주문 |
| `type` | `NEW`, `REPLACE`, `CANCEL` |
| `requestedQuantity`, `requestedPrice` | 요청 값 |
| `status` | `RECEIVED`, `SENT`, `ACCEPTED`, `REJECTED`, `UNKNOWN` |
| `idempotencyKey` | 중복 명령 방지 키 |
| `requestedAt`, `completedAt` | 처리 시각 |

### OrderEvent

주문 상태 전이의 감사 및 외부 Replay를 위한 이벤트 기록이다. 현재 상태 조회는 Order를, 변경 이력과 스트림 복구는 OrderEvent를 사용한다.

### 테이블 및 제약조건

| 테이블 | 주요 제약조건과 인덱스 |
|---|---|
| `orders` | `(api_client_id, client_order_id)` unique, `(account_id, received_at)` index, 상태·거래일 index, `@Version` 컬럼 |
| `executions` | 거래소가 보장하는 범위의 `execution_id` unique, `(order_id, executed_at)` index |
| `order_instructions` | `(order_id, client_instruction_id)` unique, `idempotency_key` unique scope |
| `order_events` | Replay scope 내 `sequence` unique, `(order_id, occurred_at)` index |

`Order`에서 `Execution` 목록을 항상 로딩하지 않는다. 체결 목록은 `ExecutionRepository`로 별도 조회하여 주문 한 건에 체결이 많아져도 Order 갱신 비용이 증가하지 않게 한다.

## 3. Service 설계

| Service | 트랜잭션 | 책임 |
|---|---|---|
| `OrderCommandService` | `@Transactional` | 신규·정정·취소 요청의 멱등성 확인, 주문/지시 저장, 상태 전이 |
| `OrderQueryService` | `@Transactional(readOnly = true)` | 주문 단건·목록 조회와 API Response Projection 생성 |
| `ExecutionService` | `@Transactional` | 거래소 체결의 중복 확인, Execution 저장, 누적 체결 및 주문 상태 갱신 |
| `OrderDispatchService` | DB 트랜잭션 밖에서 거래소 호출 | Commit된 송신 대상을 Exchange Gateway에 전달하고 결과를 별도 트랜잭션으로 기록 |
| `OrderEventService` | `@Transactional` | 상태 변경 이벤트 저장과 Outbox 생성 |

신규 주문 처리 순서:

```text
Controller 입력 검증
 → OrderCommandService
 → 계좌 권한·시장 상태 조회
 → 리스크 한도 점유 및 원장 Asset Hold
 → Order(RECEIVED/PENDING_NEW) + Outbox Commit
 → OrderDispatchService가 거래소에 즉시 전송
```

거래소 TCP 호출을 DB 트랜잭션 안에서 대기하지 않는다. 리스크·원장 단계 중 하나가 실패하면 거래소 전송 전에 이미 확보한 자원을 멱등하게 해제한다.

체결 처리 순서:

```text
거래소 체결 수신
 → executionId 중복 확인
 → Order Row 잠금 또는 @Version 검사
 → Execution INSERT
 → Order 누적 수량·평균가·상태 UPDATE
 → OrderEvent + Outbox INSERT
 → Commit
```

## 4. Repository 설계

| Repository | 주요 메서드 |
|---|---|
| `OrderRepository` | `findById`, Client 주문 ID 조회, 계좌별 cursor 조회, 체결 반영용 잠금 조회 |
| `ExecutionRepository` | `existsByExecutionId`, 주문별·계좌별 cursor 조회 |
| `OrderInstructionRepository` | Idempotency/Client Instruction 조회, 처리 상태 갱신 |
| `OrderEventRepository` | 주문 이력 및 sequence 기반 Replay 조회 |

동시 체결과 취소가 충돌할 수 있으므로 단순 `save()` 호출 순서에 의존하지 않는다. 데이터베이스 Unique Constraint, 조건부 UPDATE, `@Version` 또는 필요한 구간의 Pessimistic Lock을 선택하고 동시성 테스트로 검증한다.

## 5. 주문 상태

```text
RECEIVED
   ↓
PENDING_NEW ───────────────→ REJECTED
   ↓
NEW ─────────→ PARTIALLY_FILLED ─────────→ FILLED
 │                    │
 ├─→ PENDING_CANCEL ──┴─────────────────→ CANCELED
 ├─→ PENDING_REPLACE ───────────────────→ NEW / PARTIALLY_FILLED
 └─→ EXPIRED
```

거래소 통보의 중복과 역순을 허용하는 전이 규칙을 별도 상태 전이표로 상세화한다. 알 수 없는 조합을 임의로 덮어쓰지 않고 `UNKNOWN` 또는 Reconciliation 대상으로 격리한다.

## 6. External REST API

| Method | Path | 성공 응답 | 필요 Scope |
|---|---|---:|---|
| POST | `/api/v1/orders` | 202 | `orders:write` + 계좌 거래 권한 |
| GET | `/api/v1/orders/{orderId}` | 200 | `orders:read` + 계좌 권한 |
| GET | `/api/v1/orders` | 200 | `orders:read` |
| POST | `/api/v1/orders/{orderId}/cancellations` | 202 | `orders:write` + 계좌 거래 권한 |
| POST | `/api/v1/orders/{orderId}/replacements` | 202 | `orders:write` + 계좌 거래 권한 |
| GET | `/api/v1/executions/{executionId}` | 200 | `executions:read` + 계좌 권한 |
| GET | `/api/v1/executions` | 200 | `executions:read` |

모든 변경 API는 `Idempotency-Key`와 `@Valid` Request DTO를 사용한다. 인증 주체가 접근 가능한 `accountId`인지 Service에서 다시 확인한다.

### 신규 주문

```http
POST /api/v1/orders
Idempotency-Key: order-20260911-000001
```

```json
{
  "clientOrderId": "algo-a-20260911-000001",
  "accountId": "018f8f3a-6bc1-7bc2-a7ef-8cd43c875111",
  "instrumentId": "018f8f3a-7c11-73b2-b411-8e71ca121111",
  "market": "KRX",
  "side": "BUY",
  "orderType": "LIMIT",
  "timeInForce": "DAY",
  "quantity": "100",
  "limitPrice": "25000"
}
```

```http
HTTP/1.1 202 Accepted
```

```json
{
  "orderId": "018f8f3a-8111-76a8-87a1-c320f47b1111",
  "clientOrderId": "algo-a-20260911-000001",
  "status": "RECEIVED",
  "receivedAt": "2026-09-11T01:01:03.123456Z"
}
```

`202`는 거래소 접수나 체결을 의미하지 않는다.

### 취소 요청

```http
POST /api/v1/orders/{orderId}/cancellations
Idempotency-Key: cancel-20260911-000001
```

```json
{
  "clientInstructionId": "cancel-a-000001",
  "quantity": "60"
}
```

전체 잔량 취소는 `quantity`를 생략한다. 응답은 `202 Accepted`이며 취소 확정은 별도 이벤트로 통보한다.

### 정정 요청

```http
POST /api/v1/orders/{orderId}/replacements
Idempotency-Key: replace-20260911-000001
```

```json
{
  "clientInstructionId": "replace-a-000001",
  "newLeavesQuantity": "60",
  "newLimitPrice": "25100"
}
```

`newLeavesQuantity`는 정정 이후의 미체결 잔량을 의미한다. 거래소별 정정 규칙과 이미 체결된 수량을 반영하여 허용 범위를 검증한다.

### 체결 조회

```text
GET /api/v1/executions/{executionId}
GET /api/v1/executions?accountId={accountId}&orderId={orderId}&from={instant}&to={instant}&cursor={cursor}&limit=100
```

## 8. 주요 오류 코드

| 코드 | HTTP | 설명 |
|---|---:|---|
| `DUPLICATE_CLIENT_ORDER_ID` | 409 | Client 주문 ID 중복 |
| `ORDER_STATE_CONFLICT` | 409 | 현재 상태에서 허용되지 않는 정정·취소 |
| `INVALID_ORDER_PRICE` | 422 | 가격, 호가 단위 또는 가격제한 위반 |
| `INVALID_ORDER_QUANTITY` | 422 | 수량 또는 거래 단위 위반 |
| `MARKET_NOT_OPEN` | 422 | 현재 세션에서 주문 불가 |
| `ORDER_REJECTED` | 422 | 내부 업무 검증 거부 |
| `EXCHANGE_UNAVAILABLE` | 503 | 거래소 주문 접수 불가 |
| `ORDER_STATUS_UNKNOWN` | 503 | 거래소 최종 상태 확인 필요 |
