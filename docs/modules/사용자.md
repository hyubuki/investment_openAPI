# 사용자 업무 모듈

상태: `Draft v0.2 (B2C)`

상세 계약: [사용자 API Spec](../api/사용자-API.md)

## 1. 책임과 경계

현재 서비스는 B2C 개인 투자자를 대상으로 한다. `User`는 로그인 주체이면서 증권 계좌의
소유자다. 별도의 `Customer`, `CustomerUser`, 기관 관리자 또는 고객 위임 관계를 두지 않는다.

코드는 다음 두 최상위 업무 모듈로 구분한다.

- `user`: 개인 사용자의 가입 정보와 상태
- `auth`: Credential 검증, Access/Refresh Token, Redis Session 및 인증

계좌 소유권과 거래 가능 상태는 계좌 모듈이 관리한다. 사용자 모듈은 계좌, 주문, 잔고를
직접 변경하지 않는다. KYC/AML과 B2B 기관 권한은 현재 범위에서 제외한다.

## 2. JPA Entity

### User Entity

| 필드 | 타입 | 설명 |
|---|---|---|
| `userId` | UUID | 개인 사용자 및 계좌 소유자 식별자 |
| `email` | String | 정규화된 로그인 이메일 |
| `passwordHash` | String | 단방향 Hash. API 응답 및 로그 노출 금지 |
| `role` | UserRole | `USER`, `ADMIN`. 가입 요청으로 선택할 수 없음 |
| `status` | UserStatus | `PENDING`, `ACTIVE`, `LOCKED`, `DISABLED` |
| `failedLoginCount` | int | 연속 인증 실패 횟수 |
| `lockedUntil` | Instant? | 잠금 해제 예정 시각 |
| `lastLoginAt` | Instant? | 마지막 로그인 시각 |
| `createdAt` | Instant | 생성 시각 |
| `updatedAt` | Instant | 변경 시각 |

불변식:

- 이메일은 trim 및 소문자 정규화 후 유일해야 한다.
- Password 원문은 저장하거나 로그에 기록하지 않는다.
- 비활성 사용자는 Access Token과 Refresh Token을 사용할 수 없다.
- Client가 가입 요청에서 Role을 직접 선택할 수 없다.
- 계좌 소유권은 계좌의 `userId`로 확인하며 Request의 사용자 식별자를 신뢰하지 않는다.

### Session

Session은 `auth` 모듈이 Redis에 저장하는 인증 데이터이며 JPA Entity로 만들지 않는다.
사용자별 단일 Key를 사용해 새 로그인 시 기존 Session을 교체한다. Redis에는 Refresh Token
원문이 아니라 SHA-256 Hash, 사용자 ID, Session ID와 만료 시각만 저장한다.

Refresh Token 만료 시각을 Redis TTL로 적용하며, Token 회전은 Lua Script를 이용해 비교와
교체를 원자적으로 수행한다. 이전 Refresh Token 재사용이 탐지되면 해당 Session을 폐기한다.
Redis 장애 시 인증 검증을 생략하는 fail-open을 허용하지 않는다.

### 테이블 및 제약조건

| 저장소 | 주요 제약조건과 인덱스 |
|---|---|
| PostgreSQL `users` | `email` unique, `status`, `created_at` index |
| Redis `auth:session:user:{userId}` | 사용자별 단일 활성 Session, Refresh Token 만료 TTL |

이메일의 유일성은 사전 조회만 신뢰하지 않고 데이터베이스 Unique Constraint를 최종 기준으로 한다.

## 3. Service 설계

| Service | 트랜잭션 | 책임 |
|---|---|---|
| `UserService` | 쓰기 `@Transactional` | 가입, 이메일 정규화, Password Hash 저장 |
| `AuthService` | DB 조회 + Redis Session 처리 | 로그인, 갱신, 로그아웃, Access Token·활성 Session·사용자 검증 |
| `AuthTokenService` | Redis 쓰기 | JWT Token Pair 발급, Refresh Token 회전과 재사용 탐지 |

인증 성공 후 Redis Session 저장에 실패하면 Token을 정상 응답하지 않는다. 보호 API는 매
요청마다 Access Token의 서명·만료·용도, Redis의 현재 Session ID와 사용자 활성 상태를
검증한다.

로그인 Password가 연속으로 기본 5회 실패하면 사용자를 기본 15분 동안 `LOCKED` 상태로 전환한다.
실패 횟수 증가와 잠금 전환은 단일 조건부 UPDATE로 처리하며, 인증 실패 응답으로 로그인
트랜잭션이 롤백되더라도 실패 기록은 별도 트랜잭션에서 확정한다. 잠금 시간이 만료되면 다음
로그인 시 `ACTIVE`로 복구하고, 로그인 성공 시 실패 횟수와 잠금 정보를 초기화한다. 임계치와
잠금 시간은 `security.login` 설정으로 변경할 수 있다.

## 4. Repository 설계

| Repository | 주요 메서드 |
|---|---|
| `UserRepository extends JpaRepository<User, UUID>` | 사용자 조회, 원자적 로그인 실패 기록 |
| `RedisSessionStore` | 사용자 Session 저장·조회·회전·조건부 폐기 |

Controller는 Repository를 직접 호출하지 않는다. 외부 응답은 DTO를 사용하며 JPA Entity를
직접 반환하지 않는다.

## 5. External API

| Method | Path | 성공 응답 | 인증 |
|---|---|---:|---|
| POST | `/api/v1/users` | 201 | 불필요 |
| POST | `/api/v1/auth/login` | 200 | 불필요 |
| POST | `/api/v1/auth/refresh` | 200 | Request Body의 Refresh Token |
| POST | `/api/v1/auth/logout` | 204 | Bearer Access Token |
| GET | `/api/v1/users/me` | 200 | Bearer Access Token |

회원가입은 사용자 생성 후 자동 로그인하여 Access/Refresh Token을 함께 반환한다. 로그인도
Token Pair를 발급하며 사용자별 기존 Session을 교체한다.

일반 계좌·주문 API에는 Access Token만 전송한다. Access Token이 만료되면 Client는
`TOKEN_EXPIRED` 응답을 받은 후 `/api/v1/auth/refresh`를 한 번 호출하고, 새 Token Pair로
원래 요청을 재시도한다. 동시 만료 요청은 Client가 single-flight로 묶어 Refresh Token이
동시에 회전되지 않도록 한다.

## 6. 주요 오류 코드

| 코드 | HTTP | 설명 |
|---|---:|---|
| `EMAIL_ALREADY_EXISTS` | 409 | 이미 등록된 이메일 |
| `INVALID_CREDENTIALS` | 401 | 사용자 존재 여부를 노출하지 않는 통합 인증 실패 |
| `USER_INACTIVE` | 401 | 사용할 수 없는 사용자 |
| `SESSION_INVALID` | 401 | 만료·폐기되었거나 현재 로그인과 일치하지 않는 Session |
| `REFRESH_TOKEN_REUSED` | 401 | 이미 회전된 Refresh Token 재사용 |
| `INVALID_TOKEN` | 401 | 서명·Claim·Token 용도가 유효하지 않은 Token |
| `TOKEN_EXPIRED` | 401 | 만료된 Token |
| `UNAUTHORIZED` | 401 | Bearer Access Token 누락 또는 형식 오류 |
| `FORBIDDEN` | 403 | 인증되었지만 요청 권한이 없음 |
| `AUTHENTICATION_UNAVAILABLE` | 503 | Redis 또는 사용자 저장소 장애로 인증 상태를 확인할 수 없음 |

## 7. 내부 메시지

```text
UserRegistered
UserDisabled
SessionRevoked
```

인증 이벤트에는 Password, Access Token, Refresh Token과 Secret 원문을 포함하지 않는다.

## 8. 범위 제외

- 법인·기관 고객과 복수 사용자 소속 관계
- 사용자 간 계좌 위임과 공동 소유
- API Client, API Key, Client Scope와 Credential Lifecycle
- OAuth2 Authorization Code Provider
- KYC/AML 심사 Workflow 전체
- MFA와 Device Fingerprinting

B2B 요구가 확정되면 `Organization`과 사용자 소속 관계, 기관 소유 계좌 및 API Credential을
별도 설계한다. 현재 B2C 모델에 사용하지 않는 확장 Entity를 미리 추가하지 않는다.
