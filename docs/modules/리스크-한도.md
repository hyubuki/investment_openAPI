# 리스크·한도 업무 모듈

상태: `Draft v0.1`

상세 계약: [리스크·한도 API Spec](../api/리스크-한도-API.md)

## 1. 별도 모듈이 필요한 이유

주문 전 리스크 검사는 계좌 조회의 부가 기능이 아니다. 고객·계좌·상품·시장별 한도, 현재 주문, 미체결 예약, 포지션 및 시세를 결합해 주문 수락 여부를 결정하며 모든 신규·정정 주문의 안전 경계가 된다.
매매 모듈 안에 모든 규칙을 넣으면 주문 상태 머신과 정책 변경이 강하게 결합된다. 따라서 리스크·한도 모듈이 정책 평가와 한도 점유를 관리하고 매매 모듈은 그 결과를 사용한다. 실제 현금·증권 예약은 잔고와의 원자적 일관성을 위해 원장 모듈이 관리한다.

## 2. JPA Entity

### RiskProfile Entity

| 필드 | 타입 | 설명 |
|---|---|---|
| `riskProfileId` | UUID | 리스크 Profile 식별자 |
| `subjectType`, `subjectId` | RiskSubjectType, UUID | 고객, 계좌 또는 API Client |
| `status` | RiskProfileStatus | `ACTIVE`, `SUSPENDED` |
| `effectiveFrom`, `effectiveUntil` | Instant, Instant? | 적용 기간 |
| `policyVersion` | long | 적용 정책 버전 |

### TradingLimit Entity

| 필드 | 타입 | 설명 |
|---|---|---|
| `limitId` | UUID | 한도 식별자 |
| `riskProfileId` | UUID | 적용 Profile |
| `limitType` | LimitType | `MAX_ORDER_AMOUNT`, `MAX_DAILY_AMOUNT`, `MAX_POSITION`, `MAX_OPEN_ORDERS`, `PRICE_DEVIATION` 등 |
| `scopeType`, `scopeId` | LimitScopeType, String? | 전체, 시장, 상품 또는 자산군 |
| `value` | BigDecimal | 한도 값 |
| `unit`, `currency` | LimitUnit, String? | 수량·금액 등 단위 및 금액인 경우의 통화 |
| `action` | LimitAction | `REJECT`, `REQUIRE_APPROVAL`, `WARN` |
| `effectiveFrom`, `effectiveUntil` | Instant, Instant? | 유효 기간 |

### LimitReservation Entity

주문이 거래소에서 미체결로 대기하는 동안 일 주문금액, 최대 포지션 등 정책 한도가 중복 사용되지 않도록 노출액을 점유한다. 현금과 증권의 실제 Asset Hold는 원장 모듈이 관리한다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `reservationId` | UUID | 한도 점유 식별자 |
| `orderId` | UUID | 예약 원인 주문 |
| `accountId` | UUID | 계좌 |
| `limitType` | LimitType | 점유할 정책 한도 유형 |
| `scopeType`, `scopeId` | LimitScopeType, String? | 고객, 계좌, 시장, 상품 또는 자산군 |
| `reservedExposure` | BigDecimal | 점유한 노출액 |
| `consumedExposure` | BigDecimal | 체결 등으로 확정된 노출액 |
| `releasedExposure` | BigDecimal | 취소·거부로 반환된 노출액 |
| `status` | LimitReservationStatus | `ACTIVE`, `PARTIALLY_CONSUMED`, `CONSUMED`, `RELEASED` |
| `expiresAt` | Instant | 비정상 상태 복구를 위한 만료·검토 기준 |
| `version` | long | 동시 예약 제어 |

한도 점유는 단순 TTL 만료만으로 해제하지 않는다. 거래소에 살아 있는 주문의 점유가 자동 해제되면 한도 초과 주문이 가능해진다. 만료 시에는 Reconciliation 대상으로 전환해 주문 상태를 확인한다.

### PreTradeCheck Entity

검사 결과와 적용된 정책 버전을 감사 목적으로 기록한다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `checkId` | UUID | 검사 식별자 |
| `orderId` | UUID | 대상 주문 |
| `decision` | RiskDecision | `APPROVED`, `REJECTED`, `MANUAL_REVIEW` |
| `reasonCodes` | JSONB/String Collection | 판단 사유 목록 |
| `marketDataSequence` | long? | 검사에 사용한 시세 기준 |
| `ledgerSequence` | long | 사용 가능 잔고 기준 |
| `policyVersion` | long | 정책 버전 |
| `checkedAt` | Instant | 검사 시각 |

## 3. 핵심 규칙

- 신규 주문은 승인된 PreTradeCheck, 필요한 Limit Reservation 및 원장 Asset Hold 없이는 거래소에 전송하지 않는다.
- 매수 주문은 가격, 수수료, 세금 및 시장가 주문의 가격 변동 Buffer를 고려해 필요한 현금 Hold 금액을 산출한다.
- 매도 주문은 공매도 허용 여부와 결제 가능 수량을 검증하고 원장에 증권 수량 Hold를 요청한다.
- 정정으로 노출이 증가하면 한도와 자산의 증분 예약을 먼저 확보한다.
- 체결 시 한도 점유와 Asset Hold를 소비하고 거부·취소·만료 시 확정된 잔량만 해제한다.
- 동일 계좌의 동시 주문이 같은 한도나 가용 자산을 중복 사용하지 못하게 각 담당 모듈에서 원자적으로 처리한다.

### 테이블 및 제약조건

| 테이블 | 주요 제약조건과 인덱스 |
|---|---|
| `risk_profiles` | `(subject_type, subject_id, status)` index, `policy_version` |
| `trading_limits` | Profile·한도 유형·적용 범위·유효기간 복합 index |
| `limit_reservations` | `(order_id, limit_type, scope)` unique, `(account_id, status)` index, `@Version` 컬럼 |
| `pre_trade_checks` | `order_id`와 검사 시각 index, 정책·시세·원장 sequence 저장 |

## 4. Service 설계

| Service | 트랜잭션 | 책임 |
|---|---|---|
| `RiskEvaluationService` | `@Transactional` | 적용 정책 조회, PreTradeCheck 저장, 한도 승인 또는 거부 |
| `LimitReservationService` | `@Transactional` | 한도 잔여량 확인과 점유·소비·해제의 원자적 처리 |
| `RiskQueryService` | `@Transactional(readOnly = true)` | 외부 공개 가능 한도와 Buying Power 조회 조합 |
| `RiskPolicyService` | `@Transactional` | 운영자용 Profile과 TradingLimit 변경 및 감사 기록 |

Preview는 읽기 결과이며 실제 한도를 점유하지 않는다. 주문 처리용 `RiskEvaluationService`는 Preview 결과를 신뢰하지 않고 최신 데이터로 다시 검사한다.

## 5. Repository 설계

| Repository | 주요 메서드 |
|---|---|
| `RiskProfileRepository` | 대상 고객·계좌·API Client에 적용되는 활성 Profile 조회 |
| `TradingLimitRepository` | Scope와 유효시각에 따른 적용 한도 조회 |
| `LimitReservationRepository` | 주문별 예약 조회, 활성 예약 잠금, 사용량 합계 |
| `PreTradeCheckRepository` | 주문별 검사 이력과 정책 버전 조회 |

한도 점유는 단순한 `exists` 사전 검사 후 INSERT로 구현하지 않는다. 동시 주문에서도 한도를 초과하지 않도록 잠금 또는 원자적 조건부 갱신을 사용한다.

## 6. External API 초안

실제 주문의 승인 여부는 `POST /orders` 처리 중 수행되는 권위 있는 검사로 결정한다. 사전 조회 API는 시세와 잔고가 변할 수 있으므로 주문 성공을 보장하지 않는다.

| Method | Path | 성공 응답 | 필요 Scope |
|---|---|---:|---|
| POST | `/api/v1/order-previews` | 200 | `orders:read` + 계좌 권한 |
| GET | `/api/v1/accounts/{accountId}/trading-limits` | 200 | `accounts:read` + 계좌 권한 |
| GET | `/api/v1/accounts/{accountId}/buying-power` | 200 | `balances:read` + 계좌 권한 |

기관 Client의 계약에 따라 노출 가능한 한도만 반환하며 내부 탐지 Rule은 공개하지 않는다.

## 7. 내부 Service 계약

```text
authorizeAndReserveLimit(order) → RiskDecision + LimitReservation
consumeLimitReservation(orderId, executionId, amount)
releaseLimitReservation(orderId, reason)
reconcileLimitReservation(orderId, exchangeOrderStatus)
```

`authorizeAndReserveLimit`은 같은 주문에 대해 멱등해야 하며 승인과 한도 점유 사이에 경쟁 조건이 없어야 한다. 현금·증권 Hold는 원장 모듈의 `AssetHoldService`를 통해 별도로 요청한다.

## 8. 주요 오류 코드

| 코드 | HTTP | 설명 |
|---|---:|---|
| `INSUFFICIENT_BUYING_POWER` | 422 | 주문 가능 금액 부족 |
| `INSUFFICIENT_SELLABLE_QUANTITY` | 422 | 매도 가능 수량 부족 |
| `ORDER_LIMIT_EXCEEDED` | 422 | 건별 주문 한도 초과 |
| `DAILY_LIMIT_EXCEEDED` | 422 | 일 누적 한도 초과 |
| `POSITION_LIMIT_EXCEEDED` | 422 | 최대 포지션 한도 초과 |
| `PRICE_DEVIATION_EXCEEDED` | 422 | 기준가격 대비 허용 범위 초과 |
| `RISK_CHECK_UNAVAILABLE` | 503 | 안전한 리스크 판단 불가. Fail-closed |
