# 계좌 업무 모듈

상태: `Draft v0.2 (B2C)`

상세 계약: [계좌 API Spec](../api/계좌-API.md)

## 1. 책임과 경계

계좌 모듈은 거래 계좌의 Lifecycle, 소유 관계, 계좌 상태 및 상품별 거래 권한을 관리한다.

현금·증권의 실제 잔고와 Asset Hold는 원장 모듈이 관리한다. 주문 가능 여부와 정책 한도는 리스크·한도 모듈이 판단한다. 계좌 모듈은 이 값을 중복 저장해 독립적으로 변경하지 않는다.

## 2. JPA Entity

### TradingAccount Entity

| 필드 | 타입 | 설명 |
|---|---|---|
| `accountId` | UUID | 내부 계좌 식별자 |
| `accountNumberEncrypted` | String | 암호화된 실제 계좌번호 |
| `accountNumberHash` | String | 중복 및 검색 확인용 HMAC-SHA-256 Hash |
| `userId` | UUID | 계좌를 소유한 B2C 사용자 식별자 |
| `accountType` | AccountType | `GENERAL_BROKERAGE`(일반 위탁), `ISA_BROKERAGE`(중개형 ISA) |
| `baseCurrency` | String | ISO 4217 기준 통화 코드 |
| `status` | AccountStatus | `PENDING`, `ACTIVE`, `RESTRICTED`, `SUSPENDED`, `CLOSED` |
| `openedAt` | Instant | 개설 시각 |
| `closedAt` | Instant? | 폐쇄 시각 |
| `version` | long | 낙관적 잠금 버전 |

불변식:

- `ACTIVE` 계좌만 신규 주문을 생성할 수 있다.
- `RESTRICTED` 계좌의 허용 행위는 제한 사유와 정책에 따라 명시한다.
- `CLOSED` 계좌는 다시 활성화하지 않고 필요하면 새 계좌를 개설한다.
- 외부 응답과 로그에는 전체 계좌번호를 노출하지 않는다.
- 외부 API는 Security Principal의 `userId`와 계좌의 `userId`가 일치하는 경우에만 접근을 허용한다.
- `User` Entity와 객체 연관관계를 맺지 않고 `userId`와 데이터베이스 FK로 소유 관계를 표현한다.

### TradingPermission Entity

| 필드 | 타입 | 설명 |
|---|---|---|
| `permissionId` | UUID | 권한 식별자 |
| `accountId` | UUID | 대상 계좌 |
| `market` | TradingMarket | 거래 시장. 현재 `KR`, `US` |
| `assetClass` | AssetClass | 현재 `EQUITY`. 지원 상품 확장 시 Enum과 권한 Row 추가 |
| `side` | PermissionSide | 권한 범위. 매수·매도 모두 허용하면 `BOTH` |
| `orderType` | OrderType | 허용 주문 유형. 유형별 Row로 저장 |
| `status` | TradingPermissionStatus | `ACTIVE`, `SUSPENDED`, `REVOKED` |
| `effectiveFrom`, `effectiveUntil` | Instant, Instant? | 적용 기간 |

### AccountRestriction Entity

| 필드 | 타입 | 설명 |
|---|---|---|
| `restrictionId` | UUID | 제한 식별자 |
| `accountId` | UUID | 대상 계좌 |
| `restrictionType` | RestrictionType | `BUY_BLOCKED`, `SELL_BLOCKED`, `WITHDRAWAL_BLOCKED`, `ALL_TRADING_BLOCKED` 등 |
| `reasonCode` | String | 안정적인 제한 사유 코드 |
| `effectiveFrom`, `effectiveUntil` | Instant, Instant? | 적용 기간 |
| `releasedAt` | Instant? | 제한 해제 시각 |

### 테이블 및 제약조건

| 테이블 | 주요 제약조건과 인덱스 |
|---|---|
| `trading_accounts` | `account_number_hash` unique, `(user_id, status)` index, `@Version` 컬럼 |
| `trading_permissions` | 계좌·시장·자산군·상태 복합 index |
| `account_restrictions` | `(account_id, status, effective_from, effective_until)` index |

계좌번호는 AES-256-GCM 암호화 값과 검색용 HMAC-SHA-256 Hash를 분리하고 API 및 로그에는
마스킹 값만 노출한다. 암호화와 Hash에는 서로 다른 외부 Key를 사용한다. 계좌 폐쇄는 Row
삭제가 아니라 상태 변경으로 처리한다.

계좌번호 입력은 양 끝 공백과 하이픈을 제거한 8~14자리 숫자로 정규화하고 내부 공백·탭·개행은
허용하지 않는다. 마스킹 값은 뒤 4자리만 유지하며, 암호문과 Hash는 JSON 직렬화 대상에서
제외한다. HMAC 입력에는 `ACCOUNT:v1:` 용도 구분자를 포함한다.

계좌 상품은 일반 위탁과 중개형 ISA로 구분한다. 기존 `BROKERAGE` 데이터는 V4에서
`GENERAL_BROKERAGE`로 변환한다. 실제 거래 가능 상품은 `TradingPermission`의 시장과
`assetClass`로 판정하며, ISA의 상품 적격성·세제 요건은 별도 정책으로 검증해야 한다.
현금·신용 거래 여부도 계좌 종류가 아닌 별도 권한과 약정으로 관리한다.

`PermissionSide.BOTH`는 매수와 매도를 모두 허용하는 단일 권한 Row를 뜻한다. 실제 주문
방향은 `OrderSide.BUY` 또는 `OrderSide.SELL`만 허용한다. 향후 제한 정책은 활성 권한보다
우선하여 주문을 차단해야 한다.

계좌 권한은 구체적인 거래소가 아니라 `TradingMarket`의 `KR`, `US` 단위로 관리한다. 실제 주문이
전송·체결된 KRX, NXT 또는 미국 거래소 정보는 PowerBASE 응답을 수신하는 주문·체결 모듈에서
관리한다.

## 3. Service 설계

| Service | 트랜잭션 | 책임 |
|---|---|---|
| `AccountQueryService` | `@Transactional(readOnly = true)` | 접근 가능한 계좌, 상세, 권한 및 제한 조회 |
| `AccountLifecycleService` | `@Transactional` | 계좌 개설, 활성화, 제한, 폐쇄 |
| `TradingPermissionService` | `@Transactional(readOnly = true)` | 시장·자산군·주문 방향·유형별 유효 권한 판정 |
| `AccountAuthorizationService` | `@Transactional(readOnly = true)` | 인증 사용자의 계좌 소유권 판정 |

외부 주문 Service는 계좌 JPA Entity를 직접 수정하지 않고 `AccountAuthorizationService`와 계좌 상태 조회 메서드를 사용한다.

## 4. Repository 설계

| Repository | 주요 메서드 |
|---|---|
| `TradingAccountRepository` | `findById`, `findAllByUserIdAndStatus`, 잠금이 필요한 상태 변경 조회 |
| `TradingPermissionRepository` | 계좌·시장·상품 조건의 유효 권한 조회 |
| `AccountRestrictionRepository` | 특정 시각에 활성인 제한 조회 |

계좌 목록 API에는 Entity Graph 전체를 로딩하지 않고 Projection 또는 전용 조회 DTO를 사용한다.

## 5. External API 초안

외부 Client의 계좌 개설·폐쇄는 규제 및 내부 온보딩 절차가 필요하므로 초기 OpenAPI에서는 조회만 제공한다. 개설과 상태 변경 API는 내부 Back-office API로 분리한다.

| Method | Path | 성공 응답 | 인증/권한 |
|---|---|---:|---|
| GET | `/api/v1/accounts` | 200 | Bearer Token, 본인 계좌만 조회 |
| GET | `/api/v1/accounts/{accountId}` | 200 | Bearer Token, 본인 계좌 |
| GET | `/api/v1/accounts/{accountId}/trading-permissions` | 200 | Bearer Token, 본인 계좌 |
| GET | `/api/v1/accounts/{accountId}/restrictions` | 200 | Bearer Token, 본인 계좌 |
| GET | `/api/v1/accounts/{accountId}/balances` | 200 | Bearer Token, 본인 계좌 |
| GET | `/api/v1/accounts/{accountId}/positions` | 200 | Bearer Token, 본인 계좌 |

### 계좌 목록

```http
GET /api/v1/accounts?status=ACTIVE&cursor={cursor}&limit=50
```

```json
{
  "items": [
    {
      "accountId": "018f8f3a-6bc1-7bc2-a7ef-8cd43c875111",
      "accountNumberMasked": "****-****-7890",
      "accountType": "GENERAL_BROKERAGE",
      "baseCurrency": "KRW",
      "status": "ACTIVE"
    }
  ],
  "nextCursor": null,
  "hasMore": false
}
```

### 계좌 상세

```http
GET /api/v1/accounts/{accountId}
```

### 거래 권한 조회

```http
GET /api/v1/accounts/{accountId}/trading-permissions
```

### 계좌 제한 조회

```http
GET /api/v1/accounts/{accountId}/restrictions?activeOnly=true
```

잔고와 포지션 조회 URI는 사용자 관점에서 계좌 하위에 배치하되 데이터는 원장 Projection에서 제공한다.

```text
GET /api/v1/accounts/{accountId}/balances
GET /api/v1/accounts/{accountId}/positions
```

## 6. 내부 관리 API 초안

```text
POST /internal/v1/accounts
POST /internal/v1/accounts/{accountId}/activate
POST /internal/v1/accounts/{accountId}/restrict
POST /internal/v1/accounts/{accountId}/close
PUT  /internal/v1/accounts/{accountId}/trading-permissions/{permissionId}
```

내부 API도 인증·인가·감사 기록을 생략하지 않는다.

## 7. 주요 오류 코드

| 코드 | HTTP | 설명 |
|---|---:|---|
| `ACCOUNT_NOT_FOUND` | 404 | 계좌가 없거나 현재 사용자의 소유가 아님 |
| `ACCOUNT_NOT_ACTIVE` | 422 | 거래 가능한 계좌 상태가 아님 |
| `TRADING_PERMISSION_DENIED` | 422 | 시장·상품·주문 유형 권한 없음 |
| `ACCOUNT_RESTRICTED` | 422 | 계좌 제한으로 요청 불가 |
