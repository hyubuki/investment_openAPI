# 원장 업무 모듈

상태: `Draft v0.2 (B2C)`

상세 계약: [원장 API Spec](../api/원장-API.md)

## 1. 책임과 경계

원장 모듈은 현금과 증권의 변동을 불변 Posting으로 기록하고 잔고, 주문 가능 잔고 및 포지션 조회 모델의 근거를 제공한다.

체결 내역 자체는 매매 모듈이 관리한다. 원장은 `ExecutionCreated` 등 확정된 내부 메시지를 받아 회계적 변동을 기록한다. 과거 Posting을 수정하거나 삭제하지 않고 잘못된 기록은 반대 Posting으로 정정한다.

현금·증권의 실제 예약은 잔고와 원자적으로 일관되어야 하므로 원장 모듈이 관리한다. 리스크·한도 모듈은 필요한 예약량과 정책 한도를 판단하고, 매매 Service가 원장에 예약을 요청한다.

## 2. JPA Entity와 조회 모델

### JournalEntry Entity

| 필드 | 타입 | 설명 |
|---|---|---|
| `journalEntryId` | UUID | 분개 식별자 |
| `businessEventId` | String | 체결·입출금 등 원인 이벤트 식별자 |
| `entryType` | EntryType | `TRADE`, `DEPOSIT`, `WITHDRAWAL`, `FEE`, `TAX`, `REVERSAL` |
| `accountId` | UUID | 대상 거래 계좌 |
| `effectiveAt` | Instant | 경제적 효력 시각 |
| `recordedAt` | Instant | 원장 기록 시각 |
| `status` | EntryStatus | `POSTED`, `REVERSED` |
| `reversalOf` | UUID? | 반대 분개의 원본 ID |
| `postings` | List<Posting> | 최소 두 개 이상의 Posting |

불변식:

- 같은 `businessEventId + entryType`은 한 번만 반영한다.
- JournalEntry는 차변·대변 또는 정의된 자산 이동 규칙에 따라 항상 균형을 이룬다.
- Posted Entry의 금액, 수량 및 계정은 수정하지 않는다.
- 정정은 새로운 Reversal Entry와 필요 시 Corrected Entry로 처리한다.

### Posting Entity

| 필드 | 타입 | 설명 |
|---|---|---|
| `postingId` | UUID | Posting 식별자 |
| `journalEntryId` | UUID | 소속 분개 |
| `ledgerAccountId` | UUID | 원장 계정 |
| `assetType`, `assetId` | AssetType, String | 통화 또는 증권 상품 |
| `amount` | BigDecimal | 부호를 포함한 금액 또는 수량 |
| `bucket` | BalanceBucket | `AVAILABLE`, `RESERVED`, `PENDING_SETTLEMENT`, `SETTLED` 등 |

현금과 증권 수량은 의미가 다르므로 하나의 단순 `balance` 필드로 혼합하지 않는다.

### LedgerAccount Entity

| 필드 | 타입 | 설명 |
|---|---|---|
| `ledgerAccountId` | UUID | 원장 계정 식별자 |
| `ownerType`, `ownerId` | LedgerOwnerType, UUID | 사용자 계좌, 증권사, 수수료 계정 등 소유 주체 |
| `assetType` | AssetType | `CASH`, `SECURITY` |
| `assetId` | String | Currency 또는 Instrument 식별자 |
| `status` | LedgerAccountStatus | `ACTIVE`, `CLOSED` |

### AssetHold Entity

미체결 주문이 동일 현금이나 증권을 중복 사용하지 못하도록 실제 가용 잔고를 예약한다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `holdId` | UUID | 예약 식별자 |
| `orderId` | UUID | 예약 원인 주문 |
| `accountId` | UUID | 대상 거래 계좌 |
| `assetType`, `assetId` | AssetType, String | 현금 통화 또는 증권 상품 |
| `heldAmount` | BigDecimal | 최초 예약 금액 또는 수량 |
| `consumedAmount` | BigDecimal | 체결·수수료 등으로 확정 사용된 값 |
| `releasedAmount` | BigDecimal | 취소·거부로 가용 상태로 돌아간 값 |
| `status` | AssetHoldStatus | `ACTIVE`, `PARTIALLY_CONSUMED`, `CONSUMED`, `RELEASED`, `RECONCILING` |
| `version` | long | 동시 소비·해제 제어 |

`AVAILABLE → RESERVED` 이동은 잔고 확인과 하나의 원자적 연산으로 처리한다. TTL만으로 Hold를 해제하지 않으며 거래소 주문 상태가 불명확하면 `RECONCILING`으로 전환한다.

### BalanceProjection

원장 Posting으로부터 계산되는 조회 모델이다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `accountId`, `currency` | UUID, String | 계좌와 통화 |
| `settledAmount` | BigDecimal | 결제 완료 금액 |
| `pendingSettlementAmount` | BigDecimal | 결제 예정 금액 |
| `reservedAmount` | BigDecimal | 주문 등에 예약된 금액 |
| `availableAmount` | BigDecimal | 현재 사용 가능한 금액 |
| `asOfSequence`, `asOf` | long, Instant | Projection 반영 기준 |

### PositionProjection

| 필드 | 타입 | 설명 |
|---|---|---|
| `accountId`, `instrumentId` | UUID, UUID | 계좌와 상품 |
| `settledQuantity` | BigDecimal | 결제 완료 수량 |
| `pendingSettlementQuantity` | BigDecimal | 결제 예정 수량 |
| `reservedQuantity` | BigDecimal | 매도 주문 등에 예약된 수량 |
| `availableQuantity` | BigDecimal | 주문 가능한 수량 |
| `averageCost` | BigDecimal | 정의된 회계 정책에 따른 평균 취득가 |
| `asOfSequence`, `asOf` | long, Instant | Projection 기준 |

### 테이블 및 제약조건

| 테이블 | 주요 제약조건과 인덱스 |
|---|---|
| `journal_entries` | `(business_event_id, entry_type)` unique, `(account_id, effective_at)` index |
| `postings` | `journal_entry_id` FK, `(ledger_account_id, asset_id, bucket)` index |
| `ledger_accounts` | `(owner_type, owner_id, asset_type, asset_id)` unique |
| `asset_holds` | `order_id`와 자산 범위 unique, `(account_id, status)` index, `@Version` 컬럼 |
| `balance_projections` | `(account_id, currency)` primary/unique key, `as_of_sequence` |
| `position_projections` | `(account_id, instrument_id)` primary/unique key, `as_of_sequence` |

JournalEntry와 Posting에는 물리 삭제 API를 제공하지 않는다. 대량 원장 조회에서 `@OneToMany` 전체 로딩을 피하고 필요한 Projection Query를 사용한다.

## 3. Service 설계

| Service | 트랜잭션 | 책임 |
|---|---|---|
| `LedgerPostingService` | `@Transactional` | 업무 메시지 중복 확인, JournalEntry와 Posting 저장 |
| `AssetHoldService` | `@Transactional` | 가용 잔고 확인과 Hold 생성·소비·해제를 원자적으로 처리 |
| `BalanceProjectionService` | `@Transactional` | Posting 반영 후 Balance/Position Projection 갱신 |
| `LedgerQueryService` | `@Transactional(readOnly = true)` | 외부 잔고·포지션·거래 내역 조회 |
| `LedgerReconciliationService` | 읽기 및 보정 Workflow별 트랜잭션 | Posting 합계, Projection, 매매 체결의 불일치 탐지 |

`AssetHoldService`는 동일 계좌·자산의 예약 경쟁을 막기 위해 조건부 UPDATE 또는 명시적인 Row Lock을 사용한다. 잔고 부족 확인과 Hold INSERT 사이를 분리하지 않는다.

## 4. Repository 설계

| Repository | 주요 메서드 |
|---|---|
| `JournalEntryRepository` | 원인 이벤트 중복 조회, 계좌·기간별 cursor 조회 |
| `PostingRepository` | 원장 계정별 합계 Projection, 대사 Query |
| `LedgerAccountRepository` | 소유자·자산 기준 조회 |
| `AssetHoldRepository` | `orderId` 조회, 활성 Hold 잠금 조회, 계좌·자산별 활성 합계 |
| `BalanceProjectionRepository` | 계좌·통화 조회, sequence 조건부 갱신 |
| `PositionProjectionRepository` | 계좌·상품 조회와 cursor 목록 조회 |

## 5. External API 초안

| Method | Path | 성공 응답 | 인증/권한 |
|---|---|---:|---|
| GET | `/api/v1/accounts/{accountId}/balances` | 200 | Bearer Token, 본인 계좌 |
| GET | `/api/v1/accounts/{accountId}/positions` | 200 | Bearer Token, 본인 계좌 |
| GET | `/api/v1/accounts/{accountId}/ledger-entries` | 200 | Bearer Token, 본인 계좌 |

### 현금 잔고 조회

```http
GET /api/v1/accounts/{accountId}/balances?currency=KRW
```

```json
{
  "accountId": "018f8f3a-6bc1-7bc2-a7ef-8cd43c875111",
  "currency": "KRW",
  "settledAmount": "10000000",
  "pendingSettlementAmount": "-1000000",
  "reservedAmount": "2500000",
  "availableAmount": "6500000",
  "asOfSequence": 712003,
  "asOf": "2026-09-11T01:01:03.130000Z"
}
```

각 금액의 계산식과 부호 규칙은 회계·결제 정책 ADR에서 확정한다. Client가 응답 필드만으로 임의 합산하지 않도록 의미를 명확히 문서화한다.

일반 External Client에는 업무적으로 해석된 거래 내역을 제공하고 내부 차변·대변 계정 구조는 노출하지 않는다.

## 6. 내부 Service 호출과 메시지 Consumer

외부 Client가 원장 Posting을 직접 생성하는 API는 제공하지 않는다.

```text
placeAssetHold(orderId, accountId, asset, amount)
consumeAssetHold(orderId, executionId, amount)
releaseAssetHold(orderId, reason, amount)

ExecutionCreated   → Trade JournalEntry 생성 및 Hold 소비
ExecutionCorrected → Reversal 및 Corrected Entry 생성
OrderRejected      → 남은 Hold 해제
OrderCanceled      → 취소 확정 수량의 Hold 해제
SettlementCompleted → PENDING_SETTLEMENT → SETTLED 이동
```

각 Consumer는 원인 이벤트 ID를 기준으로 멱등해야 한다.

원장이 발행하는 주요 이벤트는 `AssetHeld`, `AssetHoldConsumed`, `AssetHoldReleased`, `JournalEntryPosted`, `BalanceProjectionUpdated`다.

## 7. 주요 오류 코드

| 코드 | HTTP | 설명 |
|---|---:|---|
| `BALANCE_NOT_AVAILABLE` | 503 | Projection 지연 또는 원장 조회 불가 |
| `POSITION_NOT_FOUND` | 404 | 해당 상품 포지션 없음 |
| `LEDGER_ENTRY_NOT_FOUND` | 404 | 거래 내역 없음 |
| `LEDGER_INVARIANT_VIOLATION` | 내부 장애 | 균형 또는 수량 불변식 위반. 외부에는 일반화된 오류 반환 |

## 8. 운영 및 대사

- 원장 Posting 합계와 Balance/Position Projection을 정기 검증한다.
- 매매 모듈의 체결 ID와 원장 `businessEventId`를 대사한다.
- Projection 지연 시간과 마지막 반영 sequence를 지표로 제공한다.
- 원장 수동 수정 API를 제공하지 않는다. 승인된 보정 Workflow가 반대 분개를 생성해야 한다.
